# サーバー側 共通運用スクリプト 設計（案）

- 状態: **提案（実装・実行・本番変更は未実施）**
- 日付: 2026-11-08
- 関連: ADR 0005〜0008（PR #3で提案中）、`docs/DEPLOYMENT.md`、`docs/OPERATIONS.md`

## 1. 目的と制約

担当者が異動しても、後任者がAIと固定スクリプトを使い、社内サーバー上で安全にデプロイ・ロールバック・起動停止・状態確認ができるようにする。

- GitHub Actions、Runnerは使わない。成果物は開発PCで作り、許可USBで持ち込む（`scripts/release-local.ps1`）。
- 既存アプリの起動方式・配置先・ポートを勝手に変えない。共通化で障害影響範囲を広げない。
- DxPlatformが止まっていても、各アプリの運用は続けられる。
- 過剰な仕組みを作らず、後任者が読んで直せる量に抑える。

## 2. 現状調査

### 2.1 リポジトリ内で確認できたこと

| 対象 | 確認結果 | 設計への影響 |
|---|---|---|
| `scripts/deploy-iis.ps1` | IIS専用。ZIPを展開検査し、配置フォルダを丸ごとcopyバックアップ → サイト停止 → 全削除 → 全コピー → 起動 → `/health/ready`。失敗時は`rollback-iis.ps1`。`-WhatIf`対応。広すぎるpath（ドライブ直下など）は拒否 | 手順の骨格（バックアップ→停止→切替→起動→確認→失敗時復旧）と`-WhatIf`、path検査は踏襲できる |
| 同上の弱点 | 配置フォルダを**その場で全削除**して書き戻す。初回（バックアップなし）の失敗時はサイトを停止したままにする。ロールバック先が健全かは確認しない。ロールバックは丸ごとcopyのため時間がかかる | Node.js向けはreleaseを世代ごとに保持し、`current`の切替だけで戻す形にする |
| `scripts/rollback-iis.ps1` | バックアップフォルダを指定して戻す。停止→全削除→全コピー→起動。起動後の健全性確認なし | 戻した後も必ずhealth確認し、結果を記録する |
| `scripts/smoke-test.ps1` | `/health/ready`をHTTPSで最大5回確認 | 一般化して`status-app`に取り込む（HTTPも許可） |
| `scripts/test-company-package.ps1` | package内部のSHA-256と、検証証跡の整合を検査。`-RequireReleasable`で試作packageを拒否 | サーバー側の`deploy-app`が配置前に必ず呼ぶ |
| Deployment API | 単一Bearer token。冪等キーなし。呼び出し元は問わない | 履歴登録は後続（journal方式）。今回のスクリプトは**API・tokenに触れない** |
| DxPlatformのHealth Check | 許可Host・許可Port（既定443）のみ。**loopbackとredirectは常に拒否** | `127.0.0.1:<port>`で待ち受けるNodeアプリは、DxPlatformから直接確認できない。サーバー側スクリプトが確認し、DxPlatformはIIS前面のHTTPS URLだけを確認する |
| Node.js・pm2・iisnode・サービス化ツールへの言及 | **リポジトリ内に一切ない** | 既存Node.jsアプリの実態はこのリポジトリからは分からない |

### 2.2 確認できていないこと

次はこの環境から調査できていません。**サーバー環境に触れていないこと**に加え、隣接する他アプリのフォルダも見ていないためです（指示のない範囲を読まない方針）。設計は、これらが**アプリごとに違う**ことを前提にしています。付録Aのシートで棚卸しします。

- 起動方式（Windowsサービス、pm2、タスクスケジューラ、手動の`node`、IISなど）
- 配置先、設定・秘密値の置き場所、ログの場所、データの場所
- 待ち受けポートと、その重複管理の有無
- 停止・復旧の現行手順、Nodeのバージョン、ネイティブモジュールの有無
- サーバー台数、サービス作成の管理権限、導入できるツール（OSS審査の可否）

## 3. 設計原則

1. **ランタイムは統一しない。操作の「型」だけを揃える。** 既存の起動方式を変えさせず、「起動・停止・状態」を同じ呼び方で扱えるようにする。
2. **アプリ単位で完全に独立させる。** 1回の操作は1アプリだけを対象にし、他アプリのプロセス・フォルダ・設定に触れない。共通のデーモンや常駐エージェントは作らない。
3. **導入は段階的に。** 参加レベルを分け、起動方式を変えられないアプリは「状態確認のみ」から始める。
4. **戻せることを先に作る。** 切替前に戻し先を確保し、切替後は必ずhealth確認し、失敗時は自動で戻す。
5. **既定は何も変えない。** すべての変更系スクリプトは`-WhatIf`に対応し、承認記録（`-ApprovalReference`）がないと動かない。
6. **秘密値を扱わない。** スクリプトは設定ファイル・環境変数・`.env`の中身を読まず、記録せず、表示しない。

## 4. 最小限の共通化案

### 4.1 共通化するもの／しないもの

| 共通化する | 共通化しない |
|---|---|
| 操作のインターフェース（5つのスクリプト） | アプリの起動方式（サービス化の方法は選択制） |
| アプリ定義ファイル`app.config.json`の項目 | アプリの設定・秘密値の形式と置き場所 |
| 配置レイアウト（`releases/`・`current`・`journal/`） | アプリのコード構造・フレームワーク・ポート番号 |
| 事前検証（SHA-256、package検査、パス安全性） | アプリ固有の業務手順（DB変更、データ移行） |
| 履歴の記録形式（journal、JSON Lines） | 他アプリを巻き込む一括操作（作らない） |

### 4.2 スクリプト（5つ）

| スクリプト | 役割 | 状態変更 | 主な必須引数 |
|---|---|---|---|
| `status-app.ps1` | 起動単位の状態、`current`のversion、health、ポート衝突、前回の失敗、中断の痕跡を表示。**常に読み取り専用** | なし | `-ConfigPath` |
| `start-app.ps1` / `stop-app.ps1` | 起動単位の開始／停止。完了を待ち、結果を表示 | あり | `-ConfigPath`、`-ApprovalReference` |
| `deploy-app.ps1` | package検証 → 展開 → 停止 → 切替 → 起動 → health確認 → 失敗時の自動ロールバック → journal記録 | あり | `-ConfigPath -PackagePath -ExpectedSha256 -ApprovalReference` |
| `rollback-app.ps1` | `current`を直前（または指定）releaseへ戻し、起動 → health確認 → journal記録 | あり | `-ConfigPath -ApprovalReference` |

ADR 0006の名称から次を変更します。`verify-package`は`deploy-app`に組み込み（単独実行する必要がないため）、`check-health`は`status-app`に統合します（スクリプト数を減らし、後任者が覚える対象を減らすため）。ADR 0006は、承認時に反映します。

### 4.3 アプリ定義ファイル（サーバー上、ACLで保護、秘密値なし）

```json
{
  "schemaVersion": 1,
  "appCode": "sample-app",
  "appRoot": "D:\\apps\\sample-app",
  "level": "Deploy",
  "runtime": { "type": "WindowsService", "serviceName": "SampleApp" },
  "health": { "url": "http://127.0.0.1:3101/health/ready", "timeoutSeconds": 15, "retryCount": 5 },
  "listen": { "port": 3101 },
  "keepReleases": 5,
  "applicationAssetId": ""
}
```

| 項目 | 意味 |
|---|---|
| `level` | `Status`（状態確認のみ）／`Control`（起動停止まで）／`Deploy`（配置・ロールバックまで）。**設定したレベルを超える操作は拒否する** |
| `runtime.type` | `WindowsService`、`IisSite`、`None`（起動停止を行わない） |
| `appRoot` | このアプリの専用フォルダ。操作は常にこの配下に限定する |
| `health.url` | 原則`127.0.0.1`。2xxで成功 |
| `listen.port` | 衝突検出用の宣言。スクリプトはポートを割り当てない |
| `applicationAssetId` | DxPlatform台帳のID（履歴登録を後続で追加するときに使用。空でもよい） |

定義ファイルの置き場所は`<ConfigRoot>\<appCode>.app.json`とし、`ConfigRoot`はサーバー固有値（例: `D:\ops\config`）。リポジトリには**実値を入れず**、実装段階（S1）で架空値の見本ファイルだけを追加する。

### 4.4 ランタイムアダプタ（最初は3種類だけ）

| type | 起動・停止の実体 | 備考 |
|---|---|---|
| `WindowsService` | `Start-Service` / `Stop-Service`、状態待ち | Nodeアプリの標準案。サービス化ツールの選択は環境確認後（ADR 0006 §7） |
| `IisSite` | `Start-Website`/`Stop-Website`と`Start-WebAppPool`/`Stop-WebAppPool` | DxPlatform自身や、IIS配下で動くアプリ用 |
| `None` | 何もしない | 外部で管理されるアプリ、およびテスト用 |

**pm2、タスクスケジューラ、手動の`node`は、アダプタを作りません。** 実装を増やすと保守対象が増え、種類ごとに失敗モードが違うためです。該当するアプリは、(a) Windowsサービスへ移行する（移行方法はアプリごとに別途決める）、または (b) 移行まで`level: Status`で参加する、のどちらかにします。

### 4.5 配置レイアウトと参加レベル

```text
<appRoot>\
  releases\<version>\      展開済み成果物（直近N世代）
  current  →  releases\<version>   ジャンクション（起動単位はこのパスで動く）
  journal\deployments.jsonl        デプロイ・ロールバックの履歴
  logs\                            アプリのログ（既存の場所を使ってもよい）
<ConfigRoot>\<appCode>.app.json    アプリ定義（appRootの外）
アプリの設定・秘密値                アプリ既存の方式（appRootの外、またはサービス環境変数）
```

| レベル | できること | 既存アプリへの要件 | 既存の動作への影響 |
|---|---|---|---|
| `Status` | 状態・health・ポート衝突の確認 | 定義ファイルを置くだけ。アプリは無改修 | なし（読み取り専用） |
| `Control` | 起動・停止 | 起動単位がWindowsサービスまたはIIS | 操作したときだけ |
| `Deploy` | 配置・ロールバック | `current`のパスから起動でき、設定・秘密値・データがreleaseの外にある | 移行時に起動単位の参照先を`current`へ変更する（アプリごとに個別計画） |

その場で上書きする「インプレース配置」は、**最初は実装しません**。必要なアプリが多い場合のみ、棚卸し結果を見て追加を検討します（保持するフォルダ指定など、事故が起きやすい機能になるため）。

## 5. 主要フロー

### 5.1 deploy-app

1. 定義の検証（`level`が`Deploy`、`appRoot`がドライブ直下でない、version文字列が安全）。
2. アプリ単位のロック取得（OSの排他オープン。プロセス終了で自動解放されるため、古いロックが残らない）。
3. ZIPのSHA-256が`-ExpectedSha256`（SharePoint承認記録の値）と一致すること。
4. 一時フォルダへ展開し、package内部のchecksumと`manifest.json`を検査。同名versionが既にあれば中止（releaseは不変）。
5. `releases\<version>`へ移動。journalへ`Pending`を記録。
6. 起動単位を停止 → `current`を新releaseへ切替 → 起動 → health確認。
7. 失敗時: `current`を直前releaseへ戻し、起動 → health確認。戻した結果も記録。戻せなければ「**要手動対応**」と明示して終了。
8. 成功時のみ、古いreleaseを`keepReleases`世代まで削除（`current`と直前は削除しない）。
9. journalを確定。終了コード0（成功）／1（失敗・ロールバック済み・要手動対応を出力で区別）。

### 5.2 失敗時の挙動

| 失敗した箇所 | 状態 | 自動対応 | 後任者の確認 |
|---|---|---|---|
| ハッシュ不一致・package検査失敗 | 何も変えていない | 中止 | 持込みファイルの再確認 |
| 展開・移動に失敗 | 稼働中のまま | 中止、一時フォルダ削除 | ディスク容量・権限 |
| 停止に失敗 | 稼働中のまま（`current`未切替） | 中止 | 起動単位の状態 |
| 切替後の起動に失敗 | 新releaseが`current` | 直前へ戻して起動 | `status-app`、アプリのログ |
| health失敗 | 同上 | 同上 | 同上 |
| ロールバックも失敗 | 停止または不整合 | なし。**要手動対応**を出力 | Runbookの復旧手順、`rollback-app -ToVersion` |
| スクリプトが途中で落ちた | `current`が無い／古いロックなし | なし | `status-app`が中断を検出し、次の手順を表示 |
| 初回（直前releaseなし）の失敗 | 起動単位は停止のまま | 停止の維持 | 原因修正後に再実行 |

### 5.3 rollback-app

直前のreleaseを既定とし、`-ToVersion`で世代を指定できる。DBは戻さない（前方互換Migrationのみとする方針、ADR 0006）。戻した後は必ずhealth確認し、結果をjournalに残す。

## 6. 安全策

- すべての変更系で`SupportsShouldProcess`（`-WhatIf`）と`-ApprovalReference`必須。承認記録の識別子はjournalに残す。
- 操作対象は`appRoot`配下に限定。パス、version、サービス名、サイト名を検証する。
- 実行アカウントに必要な権限は、対象サービスの操作と`appRoot`の変更のみ。管理者権限の昇格はスクリプトでは行わない。
- 他アプリの定義ファイルは読まない（ポート衝突検出で`listen.port`だけを読む場合を除く）。
- ログとjournalに、token、接続文字列、環境変数の値、log全文を書かない。記録する値は固定の項目に限る。
- DxPlatformのAPI・tokenには触れない。履歴登録は、journalを元にする後続スクリプトで行う。

## 7. DxPlatformとの関係

- journalの項目は、ADR 0007の履歴項目に合わせる（記録ID、アプリID、version、commit、環境、実行者、開始・終了、結果、承認記録、packageのSHA-256）。後続の同期スクリプトがそのまま送れる。
- DxPlatformのHealth表示は、IIS前面のHTTPS URLだけが対象になる。ポート直結のhealthはサーバー側（`status-app`）で見る。この二重構造を、Runbookに明記する。
- DxPlatformが停止していても、5つのスクリプトはすべて動作する。

## 8. アプリ間の差異をどう吸収するか

| 違い | 吸収方法 | 吸収できない場合 |
|---|---|---|
| 起動方式 | `runtime.type`で選択。未対応方式は`Status`で参加 | Windowsサービスへの移行を個別に計画 |
| 配置先 | `appRoot`で指定。操作はその配下だけ | 配置先が共有フォルダなどの場合は対象外 |
| ポート | 宣言された`listen.port`の衝突だけを検出 | 割り当て台帳は作らない（DxPlatform変更Cで将来対応） |
| 停止方法 | アダプタの標準停止＋タイムアウト。強制終了は自動では行わない | 強制終了が必要なアプリはRunbookに手順を書く |
| 復旧方式 | releaseの切替で戻す。DBは戻さない | データ移行を伴う変更は、アプリ側の手順で別途 |
| 設定・秘密値 | スクリプトは扱わない。releaseの外に置く前提 | releaseに設定が同居するアプリは`Deploy`に移行できない |
| Nodeのバージョン | 起動単位側（サービスの実行ファイル指定）が決める | 共通のNodeを使うアプリは版固定の計画が必要 |

## 9. 実装計画（今回は設計のみ）

| 段階 | 内容 | 本番への影響 | 受入条件 |
|---|---|---|---|
| S0 | 付録Aで既存アプリを棚卸し。サーバー環境の確認（権限、導入可能なツール）。レベルと移行順を決める | なし（調査のみ） | アプリごとの方式・レベルが一覧になっている |
| S1 | 共通ライブラリ＋`status-app`（読み取り専用）。自動テストを先に作る | なし | ローカルテスト合格。実機でも読み取りだけで確認 |
| S2 | `start-app`/`stop-app` | 操作したときだけ | 検証用アプリでの起動停止。`-WhatIf`の確認 |
| S3 | `deploy-app`/`rollback-app` | 検証用アプリのみ | 失敗パターン（ハッシュ不一致、health失敗→自動ロールバック、中断、初回失敗）の自動テストがすべて合格 |
| S4 | 検証用サーバー（Staging）でダミーアプリ（health応答だけ）を実機受入。後任者役がRunbookだけで実施 | Stagingのみ | デプロイ・ロールバック・復旧演習が手順書どおりに完了 |
| S5 | 影響の小さい既存アプリ1件をパイロット（並行稼働→切替） | 1アプリのみ | 切替後の戻し手順が演習済み |

自動テストは、`runtime.type=None`とテスト内で起動するローカルHTTP待受（`HttpListener`）で、サービスやIISなしに再現します。アダプタ自体は、`Start-Service`等を差し替えた単体テストで確認します。実機が必要なのはS4以降です。

## 10. リスクと未決事項

| リスク | 対策 |
|---|---|
| 既存アプリの方式が多様で、`Deploy`に移行できないものがある | `Status`/`Control`から始め、移行は1件ずつ。無理に統一しない |
| ジャンクション切替が環境（ウイルス対策、権限）で動かない | S4の実機受入で確認。動かない場合はディレクトリ名の切替方式を検討 |
| 運用アカウントが広い権限を持つ | 対象サービス・`appRoot`のみに限定。アカウントの設計はS0で決める |
| スクリプトの誤操作 | `-WhatIf`、承認記録必須、`level`による制限、アプリ単位ロック |
| 後任者が定義ファイルを誤編集 | 起動時に検証し、不正なら何もせず中止。見本と解説をRunbookに置く |

**決めていただきたいこと**

1. 既存アプリの棚卸し（付録A）の進め方: 担当者に記入してもらうか、私が`APPS`フォルダなどを読み取り専用で調査してよいか。
2. 最初の導入レベルを`Status`（読み取り専用）から始めてよいか。
3. インプレース配置を最初から対象外とする方針でよいか（棚卸し後に再検討）。
